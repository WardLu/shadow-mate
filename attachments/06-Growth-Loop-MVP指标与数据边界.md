## 1. 为什么需要单独的指标口径

影伴当前要验证的不是页面访问量、停留时间或积分数量，而是家长是否能用较低管理成本，让孩子持续完成现实中的学习或成长行为，并通过积分和奖励形成反馈循环。

因此必须把以下概念分开：

- 技术激活：家庭是否已经具备使用条件；
- 核心激活：家庭是否真正记录了一次有效行为；
- 留存：家庭是否在不同日期继续记录；
- Growth Loop 完成：家庭是否完成过一次奖励兑换；
- 北极星：每周有多少家庭持续产生有效成长行为；
- 技术健康：同步、TTS 和分析写入是否正常。

## 2. 已确认的指标定义

### 2.1 技术激活

一个家庭完成家庭空间创建，并至少创建一个孩子档案。家长同意记录是进入受控内测和处理儿童数据的前置条件，但不把登录、页面打开或同意页面浏览当作产品价值事件。

### 2.2 核心激活

一个已完成技术激活的家庭，首次成功记录一条学习或成长行为。

有效行为包括：

- 学习模块中的一次有效学习记录；
- 家长针对孩子完成一次正常积分项目记录，无论该项目是加分还是扣分。

不包括：

- 登录、页面浏览、查看进度；
- 人工修正、反向纠错、期初积分；
- 奖励兑换、兑现或取消本身。

进入内测后 72 小时内完成核心激活，可以作为“快速激活率”单独报告，但不改变核心激活的基本定义。

### 2.3 有效成长日

按家庭所在时区计算，一天内至少完成一条有效学习或成长行为记录。同一天的多条记录只计一个有效成长日。

人工调整、撤销、退款、期初积分和单独兑换不产生有效成长日。

### 2.4 7 日留存

从核心激活发生日起计算，接下来 7 个自然日内至少在 3 个不同日期产生有效成长日。

7 日留存不要求家庭已经兑换奖励，因为不同家庭的奖励周期可能不同；兑换作为独立的强价值指标观察。

### 2.5 Growth Loop 首次完成

家庭第一次成功完成奖励兑换，定义为：

> 首次成功兑换奖励 = Growth Loop 首次完成 / 强价值事件

这不是技术激活，也不是核心激活。奖励兑现后的再次行为是更强的后续观察指标，但不能把一次兑换直接解释为习惯已经形成。

### 2.6 北极星指标：WMGH

**每周有效成长家庭数（Weekly Meaningful Growth Households，WMGH）**：

> 一个家庭在其所在时区的自然周内，至少在 3 个不同日期完成有效学习或成长行为记录；每个家庭每周最多计 1 次。

统计规则：

- 早期以 WMGH 的绝对家庭数为主，因为样本量很小；
- 同时记录 WMGH 比例：`WMGH ÷ 已完成核心激活且已观察满 7 天的家庭数`；
- 自然周按家庭时区计算；
- 同一家庭有多个孩子时，任一孩子的有效行为都可贡献家庭的有效成长日，但家庭每周只计一次；
- 首次兑换、7 日留存、重复兑换、家长负担和音效保留率作为辅助指标；
- 同步失败、TTS 失败和分析写入失败作为技术健康指标，不替代北极星指标。

当前不为 WMGH 设定最终通过阈值。首轮数据应同时报告原始 `n/N` 和具体案例，不因 8～10 个家庭的小样本得出 PMF、统计显著性或因果结论。

## 3. MVP 漏斗

```text
F0 技术激活：家庭 + 孩子档案 + 家长同意
  ↓
F1 有可用的积分项目
  ↓
F2 核心激活：首次有效学习/成长行为记录
  ↓
F3 创建并为孩子启用至少一个奖励
  ↓
F4 首次成功兑换奖励（Growth Loop 首次完成）
  ↓
F5 奖励兑现后满 7 天，再次产生有效成长行为
  ↓
F6 核心激活后的 7 日留存：7 天内至少 3 个不同有效成长日
```

补充报告：进入内测后 72 小时内完成 F2 的快速激活率；它是首轮体验效率指标，不替代核心激活定义。

F5 只用于观察奖励兑现后的时间关联，不证明奖励导致了行为变化。F6 是激活后的个人/家庭留存口径；WMGH 是自然周口径，两者不能混为一个指标。

## 4. 数据来源与事件边界

### 4.1 产品事实优先

学习记录、积分项目、积分流水、人工调整、奖励、兑换、兑现和取消是业务事实的唯一来源。分析事件不能替代业务事实，也不能反向覆盖账本或兑换状态。

核心漏斗优先从业务事实计算；不把页面打开、停留时间、按钮点击或音效播放量当作产品价值事件。

### 4.2 分析事件的最终方案

Vercel Hobby 不支持 Custom Events，因此不依赖 Vercel 自定义事件。Quick-flomo 的 `usage_logs` 只作为命名和聚合思路参考，不直接复用，因为它同时承担 AI 用量、Token 计量和商业化统计。

MVP 的最小云端分析链路已在隔离 worktree 按私有 Supabase 边界实现，事件至少包括：

- `household_activated`
- `learner_created`
- `core_activation`
- `growth_activity_recorded`
- `retention_qualified`
- `reward_redeemed`
- `sync_failed`
- `tts_failed`

事件写入要求：

- 事件名使用 allowlist；
- 每个事件带稳定事件 ID，支持离线暂存、重试和幂等去重；
- 可记录产品标识、内部 household/profile ID、事件发生时间、家庭时区、客户端版本和必要的匿名诊断字段；
- 不记录邮箱、儿童姓名、自由文本、完整学习内容、语音文本、完整 URL、原始错误堆栈或不必要的设备指纹；
- 限制 payload 大小、写入频率和重试次数；
- 通过受控 RPC/服务端边界写入；客户端不接触 `service_role` 或 secret key；
- 统计视图或函数只在私有边界可读，客户端不可直接读取全量事件。

### 4.3 事件与隐私

本轮已完成本地同步与技术核对：

1. 隐私政策中的用途、字段和保存期限，统一到 `privacy-v2`；
2. 家长同意记录的版本和处理目的，保留 `privacy-v1` 历史兼容；
3. 家庭导出、家庭删除和撤回相关同意后的本地清理流程；
4. Supabase 表、RPC、RLS、Data API grants、频控和日志脱敏检查。

以上只证明本地代码和文档的一致性，不代表生产分析闭环已经上线；自动清理任务和生产迁移仍未完成。

## 5. 保留与删除

- 原始分析/诊断事件采用滚动 **180 天**保留；
- 到期后删除，或只保留不可逆聚合结果；
- 删除家庭数据或撤回相关同意时，同时删除该家庭的原始事件；
- 业务事实不与 180 天事件保留期绑定，按独立的数据保留、导出和删除规则处理；
- 任何延长保留、增加字段或扩大用途，都必须重新进行隐私和必要性评审。

当前状态：指标口径已确认；分析事件代码、私有表/RPC、本地迁移、隐私政策/家长同意/导出删除同步和本地测试已完成；未执行生产迁移，也未完成 180 天自动清理任务、真实家庭内测和生产验收。

下一步按以下顺序推进：

1. 继续以业务事实计算 F0～F6 和 WMGH；activity event 只承担受控诊断和漏斗补充，不替代积分/奖励事实；
2. 补齐并验收 180 天自动清理任务；在此之前，180 天只是已公开的最小保留规则，不宣称已自动执行；
3. 对 activity event 的 private 表、受控 RPC、RLS/grants、频控和家庭删除清理做独立 fact check 与 review；
4. 生产迁移只在 release gate 通过后执行，严格一次一个迁移、一次一个验证；
5. 完成受控内测后，再根据真实样本确定各指标的判断线，不把工程测试结果当作 PMF 证据。
