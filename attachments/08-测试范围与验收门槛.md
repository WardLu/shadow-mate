## 测试分层

项目使用分层门槛验证不同边界，不把单一 unit-test 覆盖率当作完整应用覆盖率：

- `npm.cmd run test:coverage` 测量 `src/lib.js`、`src/learning-state.js` 和 `src/action-lock.js` 的确定性状态与工具边界。覆盖所有已声明的学习状态转换、非法 action 防护、归一化以及 single-flight/快速操作行为；语句、分支、函数和行覆盖率均至少为 80%。
- `npm.cmd run test:e2e` 在真实 Chromium 中验证用户界面边界，包括离线流程、认证后的 profile 加载、手动同步、有限乐观并发重试、重复冲突停止与 circuit-breaker 阻断/恢复、学习者删除、家庭导出、全家庭删除、家庭/学习者重复点击保护、登出转换、OTP 重发/校验/错误状态、密码登录/修改失败、无密码登录设置，以及带确定性 Supabase API mock 的完整 `PASSWORD_RECOVERY` 密码重置回调。CI 使用 `supabase/config.toml` 描述的隔离实例运行 `supabase start`，再设置 `E2E_REAL_SUPABASE=1`，因此 `tests/e2e/cloud-real.spec.js` 验证的是隔离的本地 Auth、REST 和 RPC 服务。
- `npm.cmd run test:db` 针对由 `shadow-size/merchant-admin` 通过 `npm run supabase:local:start` 启动的共享本地 Supabase 验证数据库边界，包括 grants、RLS 隔离、状态版本冲突、保存函数、频控位置（冲突不消耗预算）和仅 owner 可执行的全家庭删除。CI 则显式使用隔离 Shadow Mate 数据库，并传入 `SHADOW_MATE_TEST_DB_URL`。

unit coverage 数字只能解释为纯逻辑覆盖率门槛，不能理解为所有 DOM 或网络语句都由 V8 覆盖。UI 和云端行为必须由对应用户旅程覆盖；数据库行为必须以 pgTAP 套件通过为准。

## 测试路由

按改动边界选择最小充分的验证层。以下命令使用 `npm run`；PowerShell 文档可使用等价的 `npm.cmd run` 形式。

| 层级 | 范围 | 入口 | 典型触发 |
| --- | --- | --- | --- |
| L0 static | 静态策略与源码检查 | `npm run check` | 文档、文案、低风险 CSS、静态配置 |
| L1 fast | 确定性逻辑与本地状态 | `npm run test:fast` | 工具、模型、控制器或 unit-test 改动 |
| L2 targeted UI | 受影响的浏览器旅程 | `npm run test:ui` 或 `npm run test:e2e -- tests/e2e/<file>.spec.js` | 导航、设置、离线、PWA 或可见交互 |
| L3 integration | 数据库、RLS、Functions、Auth 和同步边界 | `npm run test:db`、`npm run test:functions` 及受影响 E2E | schema、权限、认证、同步、导出或删除 |
| L4 full | 合并/发布边界 | `npm run test:full` | 合并、发布、依赖、公开资源、安全或高风险改动 |

`test:fast` 会运行全部 unit tests，不是 changed-only selector。`verify` 刻意排除数据库、Functions 和 E2E，不是 full-suite alias。没有设置 `RELEASE_URL` 时，`release:check` 不会验证已部署的生产 URL。每次交付都要记录所选层级、准确命令、结果、跳过的检查、环境阻塞和剩余 merge/release gate。
